## 1. 착수 전 인터뷰

작업 시작 전 A00은 작가에게 다음을 확인한다. 이미 답이 정본에 있으면 인터뷰하지 않고 원문을 인용한다.

1. 이 작업의 **의도** — 무엇이 불만이어서 시작하는가
2. **주 독자** — 플랫폼, 연령, 선호 장르 관습
3. **성공 판정 기준** — 무엇이 되면 끝난 것인가
4. **건드리면 안 되는 것** — HARD LOCK 외에 작가가 지키고 싶은 것
5. **분량과 시한**

답이 갈리면 작업 내용이 달라지는 질문만 한다. 관례적 기본값이 있는 선택은 묻지 않고 진행하며 결과에 명시한다.

## 2. 맹점 훑기

설계·감사 착수 시 다음 5축을 훑는다.

| 축 | 질문 |
|---|---|
| 부재 | 있어야 하는데 문서가 아예 없는 영역은 |
| 모순 | 두 정본이 서로 다른 말을 하는 지점은 |
| 미사용 | 설정만 있고 어느 화에서도 쓰이지 않는 항목은 |
| 과포화 | 한 층위에만 몰려 있어 다른 층이 빈 곳은 |
| 미검증 | `[ASSUMPTION]`인 채로 하위 설계가 쌓인 곳은 |

각 축에서 발견한 것은 판정 없이 먼저 나열한다. 나열 전에 결론을 쓰지 않는다.

## 3. 구현 전 함정 체크

착수 전, 이 작업이 만들 수 있는 사고를 먼저 적는다.

- 이 변경이 **되돌리기 어려운** 지점은 어디인가
- 이 변경이 **다른 층위를 깨뜨리는** 경로는 무엇인가
- 이 변경으로 **삭제될 수 있는** 복선·인과·권한은 무엇인가
- 이 작업이 **원문을 읽지 않고** 진행될 수 있는 구간은 어디인가
- 검증기·CP·발음사전 중 **함께 갱신하지 않으면 깨지는** 것은 무엇인가

명명 작업은 이 절 대신 [`naming-source-verification-gate-v1.md`](naming-source-verification-gate-v1.md)가 우선한다.

## 4. 시안 4개 — 한눈에

설계 결정에는 **서로 다른 방향의 안 4개**를 한 표에 나란히 제시한다.

| 항목 | 안 1 | 안 2 | 안 3 | 안 4 |
|---|---|---|---|---|
| 한 줄 요약 | | | | |
| 얻는 것 | | | | |
| 잃는 것 | | | | |
| 되돌리기 비용 | | | | |
| 이 안이 맞는 경우 | | | | |

규칙:

- 4개는 **정도 차이가 아니라 방향 차이**여야 한다
- 들러리 안을 만들지 않는다. 수를 못 채우면 3개로 제시하고 사유를 쓴다
- 추천안을 1개 명시한다. 나열만 하고 끝내지 않는다
- 선택된 안은 [`decision-log.md`](../00_project/decision-log.md)에 기록한다

## 5. 참고작 조사

코드 프로젝트의 `비슷한 오픈소스 참조`에 해당하는 소설 작업의 절차다.

1. 같은 **약속**(시간여행·회귀·정치 판타지)을 파는 기존 작품을 찾는다
2. 그 작품이 **1화에서 무엇을 먼저 보여주는지** 기록한다
3. 그 작품이 **어디서 독자를 잃는지** 기록한다
4. 우리가 **의도적으로 다르게 하는 지점**을 명시한다
5. 직접 차용은 A15 유사성 감사를 통과해야 한다

[`docs/00_project/reference-deconstruction.md`](../00_project/reference-deconstruction.md)에 누적한다. 참고작 이름·설정을 정본으로 승격하지 않는다.

## 6. 이탈 기록

**막히거나 원래 계획과 달라지면 그 자리에서 기록한다.** 작업이 끝난 뒤 회고로 쓰지 않는다.

| 필드 | 내용 |
|---|---|
| 시점 | 어느 단계에서 |
| 원래 계획 | 무엇을 하려 했는가 |
| 실제 | 무엇을 했는가 |
| 이유 | 원문 근거 또는 막힌 지점 |
| 영향 | 이 이탈이 뒤 단계에 남기는 것 |
| 미해결 | 아직 답 없는 것 |

정본 방향이 바뀌면 [`decision-log.md`](../00_project/decision-log.md)에, 작업 내부 이탈이면 해당 감사 문서 말미에 남긴다.

## 7. 메타 프롬프팅

AI에게 넣을 프롬프트를 AI에게 만들게 하는 절차다.

### 7.1 컨텍스트 덤핑

작업 지시 전, 이렇게 요청한다.

> 지금까지 한 대화를 기반으로 프롬프트를 만들 건데, 좋은 프롬프트를 만들기 위해 더 필요한 컨텍스트가 있다면 나에게 물어봐줘.

목적은 답을 받는 것이 아니라 **AI가 무엇을 모르는지 드러내게 하는 것**이다.

### 7.2 프롬프트 깎아내기 — 성공조건 명시

`잘 해줘` 대신 검사 가능한 조건을 쓴다.

| 나쁜 지시 | 좋은 지시 |
|---|---|
| 자연스럽게 써줘 | 첫 청취에 사람·장소·조직 중 무엇인지 구분되어야 한다 |
| 재밌게 써줘 | 1화 안에서 주인공이 대가를 치르는 선택을 1회 한다 |
| 설정 반영해줘 | 확인한 원문 경로와 문단을 각 판정마다 명시한다 |

성공조건은 **결과물을 보고 통과·실패를 판정할 수 있어야** 한다.

### 7.3 실행환경에 맞게 변환

| 환경 | 반드시 명시할 것 |
|---|---|
| Goal prompt | **중지 요건** — 언제 멈추고 물어보는가 |
| Ultracode / 대규모 실행 | **제약 조건** — 건드리면 안 되는 파일, 병합 금지 대상 |
| 이미지 생성 | 구도 · 피사체 · 스타일 · 조명 · 카메라 방향 |
| 리서치 에이전트 | 출처 기준 · 조사 범위 · 검증 방식 |
| 이 저장소의 원고 작업 | 정본 권한계층 · CP READY 여부 · 화당 최소 분량 · 병합 범위 |

### 7.4 결과물 점검

받은 결과에 대해 다음을 확인한 뒤에만 완료로 처리한다.

1. 성공조건을 **문장 단위로** 대조했는가
2. AI가 **읽었다고 주장한 파일**을 실제로 열었는가
3. **확인하지 않은 것을 확인한 것처럼** 쓰지 않았는가
4. 완료·푸시·병합 주장이 **실제 상태와 일치**하는가 (A17)

[`docs/13_writing_harness/naming-source-verification-gate-v1.md`](naming-source-verification-gate-v1.md) §4와 [`.agent/orchestra/completion-gates.md`](../../.agent/orchestra/completion-gates.md)가 이 절의 강제 장치다.
