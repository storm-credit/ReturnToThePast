# RTTP 엔진 실행 프로토콜

이 문서는 총괄 오케스트라가 실제로 어떻게 일하는지 정리한 운영 규칙이다.

---

## 1. 기본 순서

1. 현재 병목을 한 줄로 정의한다
2. `현재 작업 / 다음 작업`을 짧게 알린다
3. 총괄 단독으로 할지, 전문가를 붙일지 먼저 알린다
4. 필요한 하네스를 고른다
5. 필요한 에이전트만 고용한다
6. 결과를 병합한다
7. 스모크 감사 또는 관련 하네스를 다시 돌린다
8. self-contained pass 단위로 커밋/푸시한다

초안이 신규 화일 경우, 위 절차 앞에 아래를 끼운다.

0. `문피아 입구 레이어` 기준으로 첫 5줄과 첫 20줄을 먼저 본다

에이전트에게 넘기는 모든 packet은 최소한 아래 항목을 포함해야 한다.

- `Required Reads`
- `Locked Facts`
- `Editable Targets`
- `No-Touch Files`
- `Deliverable`
- `Stop Conditions`

세부 항목 기준은 `Packet_Baseline_Register.md`를 함께 따른다.

총괄 권한은 [CONDUCTOR_AUTHORITY_LOCK.md](CONDUCTOR_AUTHORITY_LOCK.md), 실행 규칙은 [HARNESS_RUNTIME_RULES.md](HARNESS_RUNTIME_RULES.md)를 함께 따른다.

---

## 2. 사용자에게 미리 알릴 내용

작업을 시작할 때는 아래 세 줄을 짧게 알려 준다.

- **현재 작업**: 지금 무엇을 고치거나 점검하는지
- **다음 작업**: 바로 다음에 무엇을 이어서 할지
- **실행 방식**: `총괄 단독`인지 `총괄 + 전문가`인지

예:

- 현재 작업: 마법/몬스터 2차 세부 보강
- 다음 작업: 스모크 감사 후 커밋/푸시
- 실행 방식: 총괄 + 세분화 전문가

## 3. 하네스 선택 규칙

### `Lore Audit`
- 인물, 세력, 장소, 건물, 마법, 몬스터, 타임라인

### `Foreshadow`
- 복선, 리빌, 레드헤링, 회수 빚

### `Storycraft`
- 구조, 감정선, 리텐션, 장면 압력, 엔딩 역순 설계
- 문피아 입구 레이어 적용 여부

### `Smoke`
- 빠른 정합성 확인

훅 목록은 [HOOK_CATALOG.md](HOOK_CATALOG.md), 하네스별 조합은 [HARNESS_HOOK_MATRIX.md](HARNESS_HOOK_MATRIX.md)를 우선한다.

## 4. 설정집 먼저 해야 하나

기본 답은 `예`다.

RTTP 엔진은 아래 조건이 충족되기 전엔 집필 레인을 대량 개방하지 않는다.

- 시간법칙이 잠김
- 대가 문법이 잠김
- 적대축이 잠김
- 마법/몬스터가 최소 실전층까지 채워짐
- 복선/고정점/엔딩 수렴 문서가 맞물림
- 스모크 감사 PASS

즉, 초안이 설정을 앞서가게 두지 않는다.

---

## 5. 세분화 에이전트를 언제 쓰나

항상 쓰지 않는다.

### 총괄 단독으로 충분한 경우
- 단순 동기화
- 인덱스 정리
- 짧은 문체 정책 수정
- 링크 보정

직전 초안이 없거나 끊긴 상태에서 이어 쓰는 경우에는 `Continuity_Input_Ledger.md`를 먼저 확인한다.

### 전문가를 붙이는 경우
- 설정 충돌이 넓게 퍼질 때
- 특정 도메인이 얇을 때
- 건물/의식/약방/마수처럼 세부 시트가 필요한데 코어 문서를 건드리기 전에 좁게 설계해야 할 때
- 초반 20줄이 약해서 플랫폼 입구가 막힐 때

이 경우 `serial-tension-engineer`, `hook-doctor`, `reveal-choreographer`, `chapter-inspector`를 우선 고려한다.

## 6. 역할 경계

- `MCP`는 연결과 증거를 가져온다.
- `스킬`은 작업법을 준다.
- `에이전트`는 좁은 문제를 푼다.
- `훅`은 경고와 게이트를 건다.
- `하네스`는 실행 순서를 제공한다.
- 최종 승인과 병합은 총괄만 한다.

자세한 경계는 [MCP_SKILLS_AGENTS_HOOKS_HARNESS_MAP.md](MCP_SKILLS_AGENTS_HOOKS_HARNESS_MAP.md)를 우선한다.

## 7. reasoning level 선택 가이드

사용자가 직접 선택할 수 있는 `매우높음 / 높음 / 중간`은 이렇게 보면 된다.

### `중간`
- 일반 질의응답
- 짧은 설정 수정
- 인덱스 정리
- 한두 문서 보강
- 빠른 검토

### `높음`
- 설정집 전체 점검
- 권 단위 구조 보강
- 복선/회수 설계
- 마법/몬스터 체계 설계
- 집필 전 사전 패킷 설계

### `매우높음`
- 엔딩 역순 설계
- 대규모 캐논 재설계
- 시간여행 규칙 수정
- 여러 권에 걸친 리빌/복선/감정선 재배치
- 오케스트라 시스템 자체 재구성

### 추천
- 평소 설정집/작문 설계: `높음`
- 아주 큰 뼈대 개조: `매우높음`
- 가벼운 이어서 작업: `중간`

즉, 이 프로젝트에선 `중간`이 기본은 아니고, 보통 `높음`이 가장 실용적이다.

---

## 8. 체크포인트 규칙

- pass 1개 끝날 때마다:
  - 관련 하네스 확인
  - 간단 메모 갱신
  - 커밋/푸시 여부 판단

- 주간 단위:
  - 통합 브랜치에 checkpoint push
  - 다음 큐 재정렬

- 총괄: `novel-orchestra-conductor`
- 코어 모듈: `novel-orchestra-core`
- 작품 전용 엔진층: `RTTP 엔진`
